# Editor skill docs

This directory documents every tab in the service blueprint editor's confidence-tab shell
(`Canvas`, `Calculations`, `Validation`, `Definition` — see `ConfidenceTab` in
`Wayfinder.Editor.Client/src/service-blueprint-editor/wayfinder-confidence-tabs.ts`), one topic
per subfolder. Help and keyboard shortcuts live in a dialog reachable from every tab (the
toolbar's help button, or F1) rather than a tab of their own — see
`service-blueprint-editor-help.spec.ts`. Preview and Simulation tabs existed at one point but were
removed — Preview only ever rendered one selected stage in isolation, and Simulation's own test
suite already documented it as broken past its first step, with a TODO referencing a rework that
never happened.

```
docs/skills/<topic>/SKILL.md
docs/skills/<topic>/screenshots/*.png
```

## Why "skills"

Each `SKILL.md` is written to be useful to two different readers at once:

- **A human**, browsing the repo or reading a walkthrough with real screenshots.
- **An agent**, including a future Claude Code session working in this repo — the frontmatter
  (`name`/`description`) and self-contained, single-file-per-topic shape match the real Claude
  Skill format, so these are structurally loadable as skills, not just readable as docs.

A `SKILL.md` never re-explains what's already documented elsewhere in `docs/guides/` (the
calculation grammar, the service blueprint contract, MCP authoring) — it links to that instead.
What it adds that nothing else covers is: what the UI actually looks like, the exact
`data-wayfinder-*` selectors and event contracts an automation script or agent would drive
against, and a walkthrough of the real behaviour.

## Screenshots are generated by real tests, not hand-maintained

Every screenshot in this directory is written by a `page.screenshot()` call placed inside an
**already-passing behavioural Playwright test** — never a screenshot with no assertion behind
it. If a state worth documenting wasn't covered by any existing test, a small real assertion was
added first, and the screenshot follows it. This is the mechanism that keeps these docs from
silently drifting out of date the way `docs/testing/workflow-editor-visual-tests.md` did (referenced
by a comment in `canvas-helpers.ts`, never actually written) — regenerating the screenshots is
just re-running the tests that already prove the behaviour they show.

Capture is gated behind the `CAPTURE_DOC_SCREENSHOTS` environment variable via a small shared
helper (`captureDocScreenshot` — see `Wayfinder.ReferenceApp.Tests/tests/fixtures.ts` and
`Wayfinder.Editor.Client/tests/service-blueprint-editor/support/canvas-helpers.ts`), so a routine
CI run of these suites stays deterministic and never rewrites the committed PNGs — different CI
runners render fonts/anti-aliasing slightly differently from a local machine, which would produce
noisy, meaningless diffs on every commit if capture ran unconditionally.

**To regenerate every screenshot after a real UI change**, run each project's `docs:screenshots`
script and commit the result like any other generated-but-committed asset:

```
cd Wayfinder.ReferenceApp.Tests && npm run docs:screenshots
cd Wayfinder.Editor.Client && npm run docs:screenshots
```

Each `SKILL.md`'s own "Keeping this current" section names the exact spec file(s) behind its
screenshots, if you only need to refresh one topic.

## Adding a new topic

1. Pick the real spec file(s) that already exercise the behaviour worth documenting (or add a
   small real assertion if none exists yet — never a screenshot-only test).
2. Add `captureDocScreenshot(...)` calls at the points worth showing.
3. Add the spec file to the relevant project's `docs:screenshots` script.
4. Write `docs/skills/<topic>/SKILL.md` following the shape every other topic in this directory
   uses: Overview, Walkthrough (numbered, screenshots embedded), For agents (selectors/events,
   links out to the deeper reference docs), Keeping this current.
